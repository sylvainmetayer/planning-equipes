# Moving from 3.x to 4.0

You run a 3.x instance and want to know what 4.0 will ask of you. This page is an **outline**: 4.0 is in preparation, every change that breaks something adds its paragraph here when it is merged, and no release date is promised. Do not upgrade based on this guide until 4.0.0 is published.

## Where things stand

- **3.5** is the latest version published from the development line. The `3.x` line now receives only fixes, on the `release/3.5` maintenance branch ([how it is run](publier-une-version.md#3-patcher-une-version-antérieure)).
- The 4.0 breaking changes are tracked in tickets [#271](https://github.com/sylvainmetayer/planning-equipes/issues/271) (model), [#272](https://github.com/sylvainmetayer/planning-equipes/issues/272) (freeze, versions, settings), [#273](https://github.com/sylvainmetayer/planning-equipes/issues/273) (rules), [#274](https://github.com/sylvainmetayer/planning-equipes/issues/274) (MCP and screens) and [#281](https://github.com/sylvainmetayer/planning-equipes/issues/281) (constraint batches).
- How long 3.x stays supported: see [the maintenance policy](versioning.md#combien-de-temps-une-ligne-est-corrigée).

## Before upgrading

1. Stay on the latest 3.x and read its release notes: a 3.x release may already warn about what 4.0 removes.
2. Make a [backup](sauvegarde-et-restauration.md#2-sauvegarder-à-la-main). The schema only moves forward: a database migrated to 4.0 does not go back under a 3.x image.
3. Read the "⚠️ Attention" entry of the 4.0 release notes, then the sections below.

## What changes

Each paragraph says *before*, *after* and *what you do*. The paragraphs are written as merges land; those not yet written say "Coming".

### Environment variables

#### White labelling and legal notices: twenty-six variables become eight

- **Before (3.x)**: fourteen `BRANDING_*` variables (name, organisation, logos, mascots, colours, PDF palette, support address) and twelve `LEGAL_*` (legal notices, accessibility statement, demonstration flag).
- **After (4.0)**: eight variables. `BRANDING_PRODUCT_NAME`, `BRANDING_ORGANISATION`, `BRANDING_SUPPORT_EMAIL` and `LEGAL_DEMO_INSTANCE` do not change. Four **grouped** variables, of the form `key=value;key=value` (a literal semicolon is written `\;`), replace the others: `BRANDING_IMAGES`, `BRANDING_COLORS`, `LEGAL_MENTIONS` and `LEGAL_ACCESSIBILITE`. The old names are **still read** throughout 4.x: startup warns for each one, the grouped key wins when both are set, and they will be removed in 5.0. The refusal to start without the five required notices now only applies to a public instance: see [the solve budget, the queue and the public instance](#le-budget-de-calcul-la-file-et-linstance-publique).
- **What you do**: at your own pace before 5.0, replace each old variable with its key, then remove it from your environment (compose, `.env`, deployment CI).

| Old variable | Grouped variable, key |
| --- | --- |
| `BRANDING_LOGO_URL`, `BRANDING_MASCOT_URL`, `BRANDING_MASCOT_ICON_URL` | `BRANDING_IMAGES`: `logo`, `mascot`, `mascot-icon` |
| `BRANDING_PDF_LOGO`, `BRANDING_PDF_STRIP` | `BRANDING_IMAGES`: `pdf-logo`, `pdf-strip` |
| `BRANDING_ACCENT_COLOR` | `BRANDING_COLORS`: `accent` |
| `BRANDING_PDF_HEADLINE`, `BRANDING_PDF_MUTED`, `BRANDING_PDF_ACCENT`, `BRANDING_PDF_HIGHLIGHT`, `BRANDING_PDF_PILL` | `BRANDING_COLORS`: `pdf-headline`, `pdf-muted`, `pdf-accent`, `pdf-highlight`, `pdf-pill` |
| `LEGAL_EDITEUR`, `LEGAL_HEBERGEUR`, `LEGAL_CONTACT`, `LEGAL_BASE_LEGALE`, `LEGAL_CONSERVATION`, `LEGAL_RESPONSABLE_TRAITEMENT`, `LEGAL_DIRECTEUR_PUBLICATION` | `LEGAL_MENTIONS`: `editeur`, `hebergeur`, `contact`, `base-legale`, `conservation`, `responsable-traitement`, `directeur-publication` |
| `LEGAL_ACCESSIBILITE_ETAT`, `LEGAL_ACCESSIBILITE_DATE_AUDIT`, `LEGAL_ACCESSIBILITE_CONTENUS`, `LEGAL_ACCESSIBILITE_SIGNALEMENT` | `LEGAL_ACCESSIBILITE`: `etat`, `date-audit`, `contenus`, `signalement` |

The details and an example are in [the environment variables](variables-environnement.md#marque-et-documents) and [the legal notice](mentions-legales.md).

### The solve budget, the queue and the public instance

- **Before (3.x)**: each edition set its own maximum solve duration and stop without improvement (the *Solver* screen, then *Planning rules › Solve*), under the operator's `SOLVER_SECONDS_LIMIT_MAX` and `SOLVER_UNIMPROVED_SECONDS_LIMIT_MAX` caps. Planned solves waited in a queue written to the database and **replayed at startup**. The two guards `SOLVER_MAX_SOLVES_PER_HOUR` and `SOLVER_MAX_QUEUED_JOBS` applied to any instance where they were set, and the application refused to start without legal notices on any production instance.
- **After (4.0)**:
  - **The budget is an instance setting**: `SOLVER_SECONDS_LIMIT` (900 s by default) and `SOLVER_UNIMPROVED_SECONDS_LIMIT` (180 s; `0`: never), the same for every edition, which the screen shows without changing. `SOLVER_SECONDS_LIMIT_MAX` now only bounds what a launch requests (`?seconds=`, MCP). `SOLVER_UNIMPROVED_SECONDS_LIMIT_MAX` is retired: setting it has no effect, and startup says so in a warning. Migration `V145` removes both settings from each edition; the ones an edition had set are kept in the `solve_budget_avant_4_0` table, which the application no longer reads and 5.0 will drop. A YAML scenario can no longer set its duration: the `parametresSolveur` field of an old file is ignored, and the import says so.
  - **The queue is in memory.** A restart of the application **loses** the solves that were waiting for their turn (and the ones that were running, as before). At startup, the jobs a 3.x left queued or running are marked *interrupted* in the solve history, with the reason written on the job, and the log gives their number: nothing restarts by itself. A solve that went to a remote compute machine is still followed.
  - **The quota only applies to a public instance**, declared by the new `PUBLIC_INSTANCE=true` variable. Without it, `SOLVER_MAX_SOLVES_PER_HOUR` and `SOLVER_MAX_QUEUED_JOBS` are ignored, with a startup warning if you set them. On a public instance, the refusal to start without the five required legal notices stays in place; on any other it becomes a **warning**.
- **What you do**: if an edition had set a duration or plateau of its own, find them after the upgrade in the `solve_budget_avant_4_0` table, and set `SOLVER_SECONDS_LIMIT` and `SOLVER_UNIMPROVED_SECONDS_LIMIT` to what you want for the whole instance. **If your instance is open to strangers (a public demo, for instance), set `PUBLIC_INSTANCE=true`**: without it, it no longer refuses to start without legal notices and no longer applies its quota. So that this break does not go unnoticed, an instance that does not set `PUBLIC_INSTANCE` and has its quota set, or incomplete required notices, says so at startup: it is no longer treated as public, and the warning names the variable. Set `PUBLIC_INSTANCE=false` to confirm it is not public and silence it. Before a restart, check that no solve is waiting in the queue: it would be lost. Scripts that wrote `dureeResolutionSecondes` or `plateauSecondes` through `/api/parametres-solveur` see those fields ignored; those that read `cappedFromSecondsLimit` or `cappedFromPlateauSeconds` on a job no longer find them.

### Proxy header mode is removed

- **Before (3.x)**: `REMOTE_USER_ENABLED=true`, with `REMOTE_USER_SECRET`, let an access proxy authenticate the administrator (`REMOTE_USER_ADMIN_EMAIL`) and open the staff espace without a code, through a header. A 3.x release already warned that it was "deprecated".
- **After (4.0)**: the mechanism no longer exists. The five variables `REMOTE_USER_ENABLED`, `REMOTE_USER_HEADER`, `REMOTE_USER_SECRET_HEADER`, `REMOTE_USER_SECRET` and `REMOTE_USER_ADMIN_EMAIL` have no effect any more. If one is set, startup says so in a warning and carries on; the warning disappears in 5.0. A proxy's header no longer opens anything, neither the administration nor a staff member's espace.
- **What you do**: **before** upgrading, set up [sign-in through an OIDC provider](oidc.md) or create [local accounts](comptes-locaux.md), and check that a named administrator account opens. Staff members go back to the six-digit code sent by e-mail. Then remove the `REMOTE_USER_*` variables from your environment. Your proxy can stay in front of the instance as a network filter, but it no longer replaces sign-in.

### The on-demand machine launcher is removed

- **Before (3.x)**: `SOLVER_WORKER_HOOK_URL` and `SOLVER_WORKER_HOOK_SECRET` connected a launcher that created a rented machine for the duration of a solve, with `SOLVER_WORKER_INSTANCE`, `SOLVER_WORKER_START_TIMEOUT` and `SOLVER_WORKER_IDLE_TIMEOUT`. The Solver screen showed the state of that machine, with "Prepare" and "Stop", and the repository shipped `deploy/launcher/`.
- **After (4.0)**: the application no longer starts or stops any machine. The five variables above have no effect any more: if one is set, startup says so in a warning and carries on; the warning disappears in 5.0. The **permanent worker** (`SOLVER_WORKER_URL`, `SOLVER_WORKER_SECRET`, `SOLVER_WORKER_TLS_FINGERPRINT`, `SOLVER_WORKER_DEFAULT`) does not change, nor does the rule that a remote failure fails the job. The "On this server" or "On the compute machine" choice stays on the Solver screen.
- **What you do**: if you used the launcher, rent and switch on the machine with your host's tools, start the worker on it ([the procedure](calcul-sur-une-autre-machine.md)) and set `SOLVER_WORKER_URL` and `SOLVER_WORKER_SECRET`. Without that, your solves run on this server. Then remove the five variables from your environment.

### YAML scenario format

- **Before**: the application writes `schemaVersion: 1`.
- **After**: it writes `schemaVersion: 6`. It still reads v1 files (key absent or equal to 1): they go through a chain of conversions, link by link, as the model changes during 4.x. What the chain cannot convert is ignored, and every ignored item appears in the import report's warnings, never silently. The 1 → 2 link already renames the game categories' `ninja` key to `polyvalent`, losing nothing; the 4 → 5 link converts the stands' opening hours into plages (see [Stand opening hours](#horaires-des-stands)); the 5 → 6 link renames the `journeesTypes` section to `gabarits` (see [One timeslot generator](#un-seul-générateur-de-créneaux)).
- **What you do**: nothing to read your old files, end-of-event archives or copies taken before a wipe. A v2 to v5 scenario cannot be imported into a 3.x application ("newer format"): keep a v1 export before upgrading, it is your way back. The v1 reader is removed in 5.0.

### The level of an organisation rule is chosen per edition

- **Before (3.x)**: every rule had a fixed level, hard, medium or soft, written in the catalogue. The one exception was the days-in-a-row rule, in two forms: `maxJoursConsecutifsTravailles` (weighted, medium level) and `maxJoursConsecutifsTravaillesDur` (hard, off by default). An edition could only weight a medium or soft rule, and switch a rule off or on.
- **After (4.0)**: an organisation rule has a level chosen per edition: **mandatory** (`OBLIGATOIRE`, the hard level, like a legal rule: a plan that breaks it cannot be delivered) or **preference** (medium level, strong, normal or light according to its weight). This covers the medium rules of the organisation quality category, the meal break (`coupureRepasObligatoire`) and the adult beside a minor (`mineurNecessiteEncadrementMajeur`). Legal, assignment, ad hoc and lock rules and the soft preferences have no level to choose. API: `PUT /api/constraints/{name}/niveau` (`GET /api/constraints` adds `niveauReglable` and `niveauChoisi`), MCP tool `modifier_niveau_contrainte`, `contraintes.niveaux` section of the YAML scenario (format v4, [details](../comprendre/scenario-yaml.md)). Migration `V149` adds the `obligatoire` column to `ponderation_contrainte` and rewrites nothing: the weight becomes optional so that a row can carry only the level.
- **What you do**: nothing. **Every edition keeps exactly its level and weight, hence its scores**, and old exports read as before. The days-in-a-row rule joins this mechanism, see the next section. A rule made mandatory on an edition that cannot hold it gives an infeasible plan: run the feasibility analysis before computing ([ADR 0111](repo:docs/decisions/0111-le-niveau-d-une-regle-est-le-niveau-de-son-poids.md)).

### One days-in-a-row rule

- **Before (3.x)**: two rules for one cap, `maxJoursConsecutifsTravailles` (weighted, on) and `maxJoursConsecutifsTravaillesDur` (hard, off by default). An edition that wanted a blocking cap switched the second one on. Under the hard form, the Timefold engine built the first plan day by day, in calendar order.
- **After (4.0)**: a single rule, `maxJoursConsecutifsTravailles`, whose level is chosen like that of the other organisation rules: preference (the default, at the weight it had) or mandatory. The catalogue loses one rule. The calendar construction order is withdrawn: construction goes by scarcity, on both engines.
- **What you do**: nothing for stored editions. Migration `V162` makes the rule **mandatory** in an edition that had switched the hard form on (and switches it back on if the weighted form had been switched off); otherwise the rule keeps the level, weight and switch of the weighted form, and **no score moves**. An edition that had both forms on keeps only the mandatory rule, which no longer also costs medium points. The old name `maxJoursConsecutifsTravaillesDur` is read until 5.0, with a warning, as a level: in a YAML scenario, `activees` reads it as `niveaux: {maxJoursConsecutifsTravailles: OBLIGATOIRE}`; through `PUT /api/constraints/maxJoursConsecutifsTravaillesDur` or `activer_contrainte`, switching it on makes the rule mandatory, switching it off makes it a preference again; a weight sent under that old name is refused (400), since it was a hard weight. `planning.constraint-weights.maxJoursConsecutifsTravaillesDur` is no longer read: remove it.
- **If you solve with `SOLVER_ENGINE=timefold`**: an edition that holds the rule mandatory loses the calendar order. Measured on the versioned scenarios, the final plan costs 6 to 8% more medium on `festival-realiste-canicule` and `scenario-complet`, and up to 35% on `gamme-20` and `gamme-25`, for the same budget. The direct engine, the default one, is not affected: it already built by scarcity alone ([ADR 0118](repo:docs/decisions/0118-une-seule-regle-de-jours-d-affilee-a-niveau-reglable.md)).

### Schedule rule names

- **Before (3.x)**: each legal cap existed as two rules, one for adults and one for minors: `dureeQuotidienneMaxMajeur` and `dureeQuotidienneMaxMineur` (effective work of a day), `travailContinuMaxMajeur` and `travailContinuMaxMineur` (uninterrupted stretch of work before the legal break). Each rule had its own switch and weight.
- **After (4.0)**: one rule per cap, the cap being read on the animateur's age at the timeslot's date: `dureeQuotidienneMax` (10 h for an adult, 8 h for a minor aged 16 to under 18, 7 h under 16) and `travailContinuMax` (6 h for an adult, 4 h 30 for a minor). The caps are the Labour Code's, unchanged: same breaches, same score for an unchanged setting. The catalogue goes from 46 to 44 rules; the Planning rules screen, `GET /api/constraints`, the diagnostics and the MCP tools now say one rule, with its cap per age.
- **What you do**: nothing for editions already stored. Migration `V152` merges their settings **on the most protective reading**: the rule stays on if either was (it is off only if both were), takes the hardest level and the strongest weight. What it does not rewrite: the settings history and the dosage kept with each plan still say the old names, as they tell what was done at the time. **Old names are read, with a warning, throughout 4.x, and removed in 5.0**: in a YAML scenario file (`contraintes` section, the more protective of the two settings wins, the warning appears in the import report), in `planning.constraint-weights.<old name>` (the strongest weight, warning at startup), in the `PUT /api/constraints/{name}…` routes and the rule-setting MCP tools (the answer carries the new name). Rename them before 5.0 ([ADR 0114](repo:docs/decisions/0114-une-regle-par-plafond-lue-selon-l-age.md)).
- **Before (3.x)**: the maximum weekly duration and the weekly rest also existed as two rules, one for adults and one for minors: `dureeHebdomadaireMax` and `dureeHebdomadaireMaxMineur` (effective work of the week), `reposHebdomadaireMinimal` (35 consecutive hours, for everybody) and `reposHebdomadaireMineur` (two consecutive rest days, for minors).
- **After (4.0)**: `dureeHebdomadaireMax` covers both ages (48 h by default for an adult, 35 h for a minor, the two durations of Settings › Legal) and `reposHebdomadaireMinimal` covers every animateur (35 consecutive hours, and two consecutive days within the calendar week for a minor). **These two rules keep their name**; `dureeHebdomadaireMaxMineur` and `reposHebdomadaireMineur` are withdrawn. Same breaches, same score for an unchanged setting. The catalogue goes from 44 to 42 rules.
- **What you do**: nothing for editions already stored. Migration `V154` merges the settings on the most protective reading (on if either was, hardest level, strongest weight), the row stored under the kept name counting for the adults' rule. The old names are read with a warning throughout 4.x and withdrawn in 5.0, in the same places as above: YAML scenario, `planning.constraint-weights.<old name>` (the strongest of those written), routes and MCP tools. **One trap**: the kept name no longer says "adults only". A 3.x YAML file that switched off `dureeHebdomadaireMax` alone (the adults' cap) now switches it off for both ages, with no warning, since the name did not change: re-read the `contraintes` section of your exports ([ADR 0116](repo:docs/decisions/0116-une-regle-par-plafond-hebdomadaire-et-par-age.md)).

The location rules (`eviterChangementEmplacementEloigne`, `limiterEmplacementsParJour`) and the load rules (`equilibrerCharge`, `equilibrerCreneauxPenibles`) were not merged: the bench ([place rules](../comprendre/tests-de-scenarios.md#le-banc-des-règles-de-lieu) for location, [solver bench](../comprendre/tests-de-scenarios.md#le-banc-des-règles-de-confort) for load) showed that a merge changed the plans. The *Planning rules* screen only lists the two location rules together under one title, *Spread over the day*, each rule keeping its name, level and switch.

### MCP tools

**Before**: 157 tools whose names almost all start with a verb (`lister_stands`), with about ten exceptions (`equite_planning`, `volumes`…). **After**: tools are named `<verb>_<object>`, the verb taken from a closed set ([ADR 0100](repo:docs/decisions/0100-convention-de-nommage-des-outils-mcp.md)), some are grouped or removed. A tool is published only under its current name, except for the old names kept until 5.0 next to the new one, whose description starts with « Ancien nom » (those of the day review and of the timeslot generator). The mapping, old name then new name or "removed", is in [the old tool names](../comprendre/mcp-outils.md#anciens-noms-doutils), filled in as 4.0 changes land (for now no tool is renamed).

**What you do**: if you have written instructions, prompts or scripts that name tools, reread them against this table; an assistant that reconnects rereads the tool list and has nothing else to change.

### The edition's settings in four sections

- **Before (3.x)**: four API roots (`/api/parametres-legaux`, `-qualite`, `-solveur`, `-notifications`), eight MCP tools (`consulter_parametres_legaux`, `modifier_parametres_legaux`, and their three counterparts) and, in a YAML scenario, the top-level keys `parametresLegaux`, `parametresQualite` and `parametresSolveur`.
- **After (4.0)**: the settings have four sections, `legal`, `organisation` (the former "quality"), `notifications` and `calcul` (the former "solver", reduced to the end-of-solve mail, with the instance's budget read-only). The API serves them as `GET /api/parametres` (all four) and `GET`/`PUT /api/parametres/<section>`, which refuses with a 400 a field that is not of the section. Each section carries `modifieLe`, which the `PUT` sends back: a section written since answers `409` (`MODIFICATION_CONCURRENTE`), and without `modifieLe` nothing is checked (migration `V150`, one column per table). Two MCP tools replace them: `consulter_parametres` and `modifier_parametres`, each with a `section` argument (same refusal). A scenario groups them under one key, `parametres:` (`legal` and `organisation`; notifications are not part of it, as before, and the solve budget is no longer an edition setting). These two changes have no SQL migration of their own: the budget's is described above.
- **What you do**: nothing for your data or files: v1 and v2 scenarios are converted on reading. The former API roots still answer, as aliases declared obsolete (`deprecated` in the OpenAPI), throughout 4.x, and ignore an unknown field as before, and a `modifieLe` they now return without checking it (the last writer wins, as before); they are removed in 5.0, like the old format. If a script or a prompt names the old MCP tools, reread it against the [MCP tools](../comprendre/mcp-outils.md#anciens-noms-doutils) table; no tool alias is published.

On screen, *Settings* now has one tab per section (*Notifications*, then *Legal*, *Organisation* and *Solve* behind "Advanced settings"). Three addresses change, and each one redirects: `/regles?onglet=calcul` becomes `/parametres?onglet=calcul` (the *Solve* tab of *Planning rules* joined the settings), `/parametres?onglet=emails` and the `#emails` anchor of the *Edition* tab become `/parametres?onglet=notifications`, and `/parametres?onglet=legaux` becomes `/parametres?onglet=legal`. The *Legal* and *Quality* tabs of *Planning rules* merged into one *Rules* tab with three blocks; their former addresses (`/regles?onglet=legal` and `?onglet=qualite`) still lead there. Update your bookmarks when convenient; nothing else to do.

### The "ninja" game category becomes "all-rounder"

- **Before**: the game category that makes its holders available on every stand was called "ninja": `ninja` flag of the game categories (REST, YAML, CSV, MCP tools) and `typologie.ninja` column.
- **After**: it is called "all-rounder" (`polyvalent`). Migration `V140` renames the column and its index, and fixes the field names already recorded in the action journal. The rule's name (`preserverBufferPolyvalents`), its weights and its switch do not change. API responses, YAML and CSV exports and the MCP tools' field say `polyvalent`; the derived keys follow (`polyvalentConfigure` of the fragility and tension reports, `typologiePolyvalenteDefinie` of the staffing-need report). The screens say "All-rounder category". The stands' `premium` flag keeps its name and is displayed as "Premium stand".
- **What you do**: nothing for your data or your files. The old names are still read throughout 4.x (`ninja` JSON and YAML key, `ninja` CSV header, the latter flagged line by line in the import report) and removed in 5.0. Only your scripts that *read* a `ninja` key from an API response or an export need to move to its new name.

### Stand opening hours

- **Before**: a stand stated its hours through **recurring rules** ("every day from 10:00 to 12:00 then from 14:00 to closing", or every Saturday, or a date range, or specific dates), plus dated exceptions. The application folded these rules at every read, and the screen offered to "compact" dated entries into rules.
- **After**: a stand carries a **list of dated plages**, an opening or a closure per day ([decision 0104](repo:docs/decisions/0104-les-horaires-d-un-stand-sont-une-liste-de-plages-datees.md)), and that is all the resolution reads. A recurrence stays the stand's **model** ("Saturday and Sunday, 10:00-18:00"): while the edition has no dates it waits; as soon as the edition has timeslots, the model is **unfolded** into plages over the days of the event, then on every day the edition gains afterwards. Migration `V159` converts your rules over the days of each edition that has timeslots (from the first to the last, plus the day after a timeslot that runs past midnight), **with the exact reading the application had of them**: a test replays it on each shipped scenario and compares, day by day, the windows obtained with those of 3.x. The YAML moves to version 5 likewise, the `plages` key replacing `ouvertures` and `indisponibilites`, and `horaires` becoming the stand's model.
- **What you do**:
  - **Export each edition to YAML before upgrading** (Files, "Export the current data as a scenario"). It is your way back, and the only way to recover the detail of your rules: the migration does not go back down.
  - **An edition with no timeslot at all keeps its rules as the model**, as they are: nothing is converted or lost, no warning. They are laid on the days of the timeslots you create next, and the future timeslot generator will start from them.
  - **The rules are neither deleted nor renamed**: they stay the model of their stand, in the same tables, including for an edition that has timeslots. A day added afterwards therefore gets the stand's schedule, as in 3.x. An edition's YAML carries the rule (`horaires`) and its plages.
  - **Screen**: a stand's fiche shows its **recurring model** at the top, editable ("every Saturday and Sunday from 10:00 to 18:00, headcount 2"), and below it the list of its **dated windows**, each marked *model* or *typed*. You add an opening or a closure by hand, and remove a window or a whole day. The fiche's day × timeslot grid is gone: *operator action*, none, beyond telling organisers where to enter hours. A saved rule is kept as the model and, when the edition has timeslots, unfolded at once into windows over the days of the event, never refused; a window laid by the model and removed by hand does not come back, until the model's rules change. **The "Compact the hours" action is removed**: the `POST /api/stands/compactage-horaires` route and the MCP tool `compacter_horaires_stands` no longer exist, a dated plage having no rule left to fold into (see [the old tool names](../comprendre/mcp-outils.md#anciens-noms-doutils)). On the assistant side, `consulter_stand` and `lister_stands` show each stand's model (`horaires`), `creer_horaire_stand` adds to it (a rule identical to an existing one changes nothing) and `supprimer_horaires_stand`, which stays, clears the model **and** the plages it unfolded, but keeps the hand-entered ones.
  - **API**: a stand's record publishes its plages under `plages` (with `id`, `mode` and `depliee`), and three routes lay or remove a plage (`POST /api/stands/{id}/plages`, `DELETE /api/stands/{id}/plages/{plageId}` and `DELETE /api/stands/{id}/plages?date=`). The `ouvertures` and `indisponibilites` keys are flagged deprecated in the OpenAPI, but read and returned until 5.0: a script that sends them keeps working, a script that reads them must move to `plages` before 5.0.
  - **Assistants (MCP)**: `ajouter_ouverture_stand` and `ajouter_fermeture_stand` become `creer_plage_stand` (`mode` argument), `effacer_plages_stand` becomes `supprimer_plage_stand` (by `plageId` or by `date`), `ajouter_horaire_stand` becomes `creer_horaire_stand` and `effacer_horaires_stand` becomes `supprimer_horaires_stand`. A stand's views return `plages` instead of `fermetures` and `ouvertures`. Instructions that name the old tools follow the table of [MCP tools](../comprendre/mcp-outils.md#anciens-noms-doutils).

### Carpooling is reduced to validated or not

- **Before (3.x)**: an "I'm coming with…" request went through four states (`EN_ATTENTE`, `VALIDEE`, `ECARTEE`, `ANNULEE`), the organisation could write a reason, and three e-mails went out: validation, request set aside, grouped arrival cancelled.
- **After (4.0)**: a request is not validated (`EN_ATTENTE`) or validated (`VALIDEE`). Setting a request aside or cancelling a grouped arrival deletes the request, with no reason and no e-mail. One e-mail remains: the validation, sent to each member. The `arriveeGroupee` rule does not change, nor does the adjustment a validation creates. Migration `V142` takes the requests already set aside or cancelled out of the table, and the reason column: they are kept, reason included, in the `declaration_coequipier_avant_4_0` archive, which the application no longer reads and which 5.0 will drop ([retention](conservation-des-donnees.md#larchive-du-covoiturage-3x)); the API no longer returns `reason`, and the `.../ecart` and `.../annulation` routes answer `204` with no body. The status returned by `lister_demandes_covoiturage` has only two values.
- **What you do**: nothing for your data. After a cancellation, tell the group yourself, since no e-mail goes out any more. A script that read `ECARTEE`, `ANNULEE` or `reason` must do without. Add the archive to your record of processing, with its retention ([the limits to record](rgpd-limites-a-consigner.md#les-demandes-de-covoiturage)).

### Snapshots become versions

- **Before (3.x)**: a kept plan was called a "snapshot" (table `plan_snapshot`), and the word covered three things told apart by two flags: the copy asked for by hand, the one taken automatically before a solve (`automatique`) and the publication (`publie_le`). The routes were `/api/planning/snapshots` and the MCP tools `capturer_instantane`, `lister_instantanes`, `consulter_instantane`, `comparer_instantanes`, `restaurer_instantane` and `supprimer_instantane`.
- **After (4.0)**: one type, the **version**, with three origins written in a column: `MANUELLE`, `AVANT_CALCUL`, `PUBLIEE` ([ADR 0108](repo:docs/decisions/0108-un-seul-type-version-a-trois-origines.md)). Migration `V143` renames the table `version_plan`: no row is copied, moved or changed, and the delivery traces that point at a publication still do. The routes become `/api/planning/versions`; the old `/api/planning/snapshots` roots still answer, with the same body, and the response still carries `automatique` next to the new `origine` field. The MCP tools become `creer_version`, `lister_versions`, `consulter_version`, `comparer_versions`, `restaurer_version` and `supprimer_version` (no aliases, like every tool), and their answers say `origine` in place of `automatique`. The comparison, the purge of automatic copies (`planning.snapshots.automatiques-conservees`) and the rule that forbids deleting the last publication, or the one that is the reference of an elapsed day, do not change. The `planning.publie` webhook event keeps its `instantaneId` field.
- **What you do**: nothing for your data. A script that calls `/api/planning/snapshots` must move to `/api/planning/versions` before 5.0, which removes the alias and `automatique`. Instructions, prompts or scripts that name a `*_instantane*` tool follow the table of the [MCP tools](../comprendre/mcp-outils.md#anciens-noms-doutils). Before upgrading, your usual database backup is enough: going back to 3.x means restoring that backup, since 3.x does not know `version_plan`.
- **On screen**: the word "snapshot" goes away, *Solver › Plan versions* says the origin of each version (manual, before a solve, published), and the comparison has a screen of its own, *Compare two versions* (`/comparer`), which compares two versions of the plan or, in its *Editions* view, the reference data of two editions. The old addresses follow: `/editions/comparer?a=…&b=…` leads to `/comparer?vue=editions&a=…&b=…`, and a link `…?onglet=versions&comparer=…` leads to `/comparer?vue=versions&comparer=…`. Nothing to do on your side but update your bookmarks.

### The copy before a wipe becomes a YAML export

- **Before (3.x)**: before "Empty this edition", a scenario import or a restore, the application stored the edition's scenario (YAML text) **and**, in a separate JSON column (`sauvegarde_avant_vidage.plan`), its schedule; the restore ran the import, then dedicated code put the seats and locks back.
- **After (4.0)**: the copy is **one YAML export**, whose last section, `plan:`, carries the seats and locks; the restore is the normal import of that file, which puts the schedule back ([ADR 0112](repo:docs/decisions/0112-la-copie-avant-vidage-est-un-export-yaml-avec-son-plan.md)). Migration `V147` only makes the `plan` column optional: **no row is copied, rewritten or deleted**. The copies already stored by 3.x remain restorable and downloadable: their column is read as the `plan:` section of the same file. The downloaded file of a recent copy carries that section; it remains a valid v3 scenario; imported by hand, it brings back only the scenario (the `plan:` section is ignored with a warning), only the restore puts the schedule back. The rights (administrator only) and the retention (that of the edition, no purge) do not change.
- **What you do**: nothing for your copies. If your processing register describes "scenario and schedule by identifiers", it stays accurate; add that the file is a full YAML export, to be kept like the database ([copies before a wipe](rgpd-limites-a-consigner.md#les-copies-avant-vidage)). The read path of the old column is removed in 5.0, like the v1 reader: before 5.0, restore or delete the 3.x copies you still need.

### The measures of an edition have one table and one screen

- **Before (3.x)**: the history of each solve's indicators lived in `kpi_historique`, the frozen realised measure of a finished edition in `kpi_realise`; one was read at the bottom of *Solver › Plan versions* (`GET /api/kpi/historique`), the other under *Today › Realised vs planned* (`GET /api/planning/realise`), and three MCP tools served them (`lister_kpi_historique`, `supprimer_kpi_historique`, `realise_vs_planifie`).
- **After (4.0)**: a single table, `mesure_edition`, with a `nature` column (`INDICATEURS` or `REALISE`) ([ADR 0113](repo:docs/decisions/0113-une-table-et-un-ecran-pour-les-mesures-d-edition.md)). It still has **no foreign key**: the measure outlives the edition. The realised is still **written only once** (`ON CONFLICT DO NOTHING`), and freezing it again is still a SQL deletion of its rows. One screen, *Edition measures* (`/mesures`, off the menu: a link at the top of *Today*, where the tab was, the palette and the help), with two views in the address: `?vue=realise` (the default) and `?vue=indicateurs`. The API moves under `/api/mesures-edition` (`/indicateurs`, `/realise`, `/realise/detail`, `/realise/export`, `/realise/precedente`). The MCP tools become `lister_mesures_edition`, `supprimer_mesure_edition` and `comparer_realise_planifie`.
- **What you do**: nothing for your data. Migration `V148` copies every row (the history's identifiers are kept), then keeps the old tables under the names `kpi_historique_avant_4_0` and `kpi_realise_avant_4_0`: the application neither reads nor exports them, and 5.0 deletes them. Once 4.0 is in place and going back to 3.x is ruled out, `DROP TABLE` removes them with no effect on the application. A script that froze an edition again must write `DELETE FROM mesure_edition WHERE nature = 'REALISE' AND edition_id = '…'`. The old paths `/api/kpi/historique` and `/api/planning/realise` still answer, as aliases declared obsolete (`deprecated` in the OpenAPI), throughout 4.x: move to the new ones before 5.0. The old screen addresses (`/realise`, `/aujourdhui?onglet=realise`) lead to the measures screen. Re-read any instructions, prompts or scripts that name one of the three tools against the table of [old tool names](../comprendre/mcp-outils.md#anciens-noms-doutils).

### The weighting history joins the action journal

- **Before (3.x)**: a rule's panel (*Planning rules*) showed every change of weight or activation, values included, and the solves that followed (`GET /api/constraints/historique`, `GET /api/constraints/{name}/historique`, MCP tool `consulter_historique_ponderation`); the rows lived in `ponderation_contrainte_historique`, for the whole life of the edition.
- **After (4.0)**: there is only one journal. *Settings › History*, "Rules" filter (`GET /api/historique?nature=regles`), says which rule changed activation, weight or level, when and by whom, **without the value**: the journal keeps none, and it expires like the rest. The two routes and the tool are removed, with no alias (the tool appears as "retiré" in [the former tool names](../comprendre/mcp-outils.md#anciens-noms-doutils)). A scenario import and an edition duplication no longer leave one row per rule: the journal says the import or the duplication, not each rule they set.
- **What you do**: nothing for your data. Migration `V158` **does not migrate** the old rows, which carry values the journal refuses: it renames the table to `ponderation_contrainte_historique_avant_4_0`, which the application neither reads nor exports and 5.0 deletes. To keep those values, export the table before upgrading; once 4.0 is in place and going back to 3.x is ruled out, `DROP TABLE ponderation_contrainte_historique_avant_4_0` removes it with no effect on the application. A script that read the two routes or the tool must read the journal, or do without the values.

### The lock has only three types

- **Before (3.x)**: a lock could target a staff member over the whole event (`ANIMATEUR`), a stand over the whole event (`STAND`), a day (`JOUR`), a timeslot for every stand (`CRENEAU`) or a staff member on a timeslot (`ANIMATEUR_CRENEAU`, also laid by an accepted swap).
- **After (4.0)**: three types ([ADR 0109](repo:docs/decisions/0109-trois-types-de-verrou.md)): staff member + timeslot (`ANIMATEUR_CRENEAU`), stand + day (`STAND_JOUR`), day (`JOUR`). Migration `V151` converts each old lock into what it froze on the saved plan, so that plan does not move at the next solve:

| Old lock | Becomes |
| --- | --- |
| `ANIMATEUR` | one staff member + timeslot lock per timeslot where the staff member holds a seat |
| `STAND` | one stand + day lock per day on which the stand has seats |
| `CRENEAU` | one staff member + timeslot lock per staff member holding a seat on that timeslot |
| `JOUR`, `ANIMATEUR_CRENEAU` | unchanged |

  A lock for which the plan has no matching seat froze nothing and disappears. The `animateurVerrouilleFige` rule is removed: a staff member is no longer locked "everywhere", so nothing forbids giving them a seat elsewhere, and empty seats are not frozen (as before). The number of rules goes from 47 to 46. The `verrouiller` MCP tool keeps its name; its `type` argument takes `ANIMATEUR_CRENEAU`, `STAND_JOUR` or `JOUR`, and the API refuses the old values with a `400`. The `plan:` section of a YAML file (the one of the copy before a wipe) carries only these three types; a file naming an old one is read with the same conversion, and each converted lock is reported by a warning.
- **What you do**: nothing for your locks. The locks of older editions are converted the same way. A script or prompt that laid an `ANIMATEUR`, `STAND` or `CRENEAU` lock must lay one lock per timeslot or per day. A copy before a wipe taken in 3.x that contains such locks stays restorable: its locks are converted on reading, the same way, without the stored copy being rewritten.

### "Exclude from the publication" is removed

- **Before (3.x)**: the review list of a publication had a box per person, and the "Who received which version" table a "Defer" button: an unticked person received nothing and stayed to be notified. The body of `POST /api/planning/publication` carried `exclusions`, and the MCP tool `publier_planning` an `exclusions` argument.
- **After (4.0)**: a publication notifies **everybody** concerned. The boxes, the "Defer" button, the `exclusions` field and the MCP argument are gone; a client still sending `exclusions` gets a `200`: the field is ignored, and the answer carries an `avertissements` field saying the exclusion no longer exists (read that way until 5.0). "Notify only a few people" (`cibles`: the two people of an accepted swap, a replacement) stays, and defers the others as before. Existing exclusions are **ignored**: the deferred person was already to be notified, the next publication writes to them. The home alert closes person by person, once a publication has really notified that person (successful send); a person with no address, whose send fails or whom the publication defers keeps it. Migration `V160` stores every person whose last publication line was a deferral in `exclusion_publication_avant_4_0`, which the application no longer reads and 5.0 will drop, and the home screen shows one alert per person, stored **by identifier only**, never by name (the screen looks the name up when displaying, from the fiche). 3.x did not tell an exclusion deferral from a "notify only a few people" one: the archive keeps them all.
- **What you do**: before running the first 4.0 publication, read the home alerts (or `SELECT animateur_id FROM exclusion_publication_avant_4_0`): those people will receive their planning. If you wanted to call them first, do it beforehand. A script that sent `exclusions` must use `cibles`. Add the archive to your processing register ([retention](conservation-des-donnees.md#larchive-des-exclusions-de-publication-3x)): `DROP TABLE exclusion_publication_avant_4_0;` removes it with no effect on the application.

### The reference data freeze becomes the phase of the edition

- **Before (3.x)**: reference data was frozen family by family (stands, timeslots, game categories and locations, skills), each laid down and lifted on its own in Settings (table `gel_referentiel`). Nothing froze by itself, not even after a publication.
- **After (4.0)**: an edition has a **phase**, Preparation, Solving, Published or Finished ([ADR 0115](repo:docs/decisions/0115-la-phase-de-l-edition-remplace-le-gel.md)), and the phase is what freezes. In Solving and Finished, the four families are frozen. In Published, the structure (stands, timeslots, game categories and locations) is frozen but the staff fiches, skills included, stay editable; the structure can be **unblocked** for a last-minute change without leaving the phase, and the next publication freezes it again. **The first publication moves the edition to Published**; every other change of phase is an explicit gesture (`PUT /api/editions/courant/phase`). Consignes, availability, adjustments and locks remain free in every phase, and the frozen past (`PASSE_FIGE`) stays an instance setting, unrelated to the phase.
- **Migration `V155` derives the phase from the state of each edition, and this mapping loses information**:

| 3.x state | 4.0 phase |
| --- | --- |
| At least one publication, no structure family frozen | Published, structure unblocked: nothing closes at the upgrade, the next publication freezes it |
| At least one publication, a structure family frozen | Published, structure frozen **as a whole** |
| No publication, at least one family frozen | Solving: the **four** families frozen |
| No publication, no family frozen | Preparation |

  What is lost: the per-family detail. An edition that had frozen only its stands sees its timeslots, game categories and locations and skills frozen too; a published edition that had frozen its skills finds them editable again; the freeze date of each family becomes a single phase date. The `gel_referentiel` table stays in place, read by nothing and left out of the SQL export, for a way back to 3.x, and 5.0 drops it.
- **What you do**: after the upgrade, open each ongoing edition and check its phase on the home page ("Phase of the edition" line) or in Administer › Editions. If a family is frozen while you wanted it open, change the phase there: go back to Preparation to reopen the four families, or, in Published, click "Unblock the structure" (a banner says so as long as it is unblocked). The "Reference data freeze" card of Settings, *Edition* tab, no longer exists. The MCP tools `figer_referentiel` and `lever_gel` are replaced by `modifier_phase_edition` (`phase` argument, or `structure` to unblock and freeze again): an assistant or prompt that names them must change the name, with no alias. Until 5.0, the `PUT` and `DELETE /api/editions/courant/gel/{famille}` routes remain aliases of the phase (freezing one family in Preparation freezes them all); a script that calls them must move to `PUT /api/editions/courant/phase` and `/api/editions/courant/deblocage-structure` before 5.0. After a publication, a script or import that changed stands or timeslots is refused with `409 REFERENTIEL_FIGE` until the structure is unblocked.

### The day validation becomes the state of the day

- **Before (3.x)**: a day could be "reviewed and accepted" (`/api/validations`), and separately carry a day lock; the two were independent, and the review progress only counted accepted days.
- **After (4.0)**: each day has a state, **to review**, **reviewed** or **frozen** ([ADR 0121](repo:docs/decisions/0121-l-etat-de-la-journee-se-lit-sur-la-relecture-et-le-verrou.md)). Frozen means carrying a day lock: a solve no longer touches it. Reviewed freezes nothing, and the review is lost when a solve recomputes the day, as in 3.x. The state is read with `GET /api/etats-journee` and changed with `PUT /api/etats-journee/{jour}` (`A_RELIRE`, `RELUE`, `FIGEE`): only `FIGEE` lays the lock, only `RELUE` and `A_RELIRE` remove it. The state depends neither on the edition's phase nor on the active edition. Nothing is migrated: a reviewed day is reviewed, a day under a day lock is frozen, reviewed or not. **What changes for you**: a day locked for the whole day without having been accepted now counts as reviewed in the progress ("3 days out of 12"), in the publication panel and in a solve's summary.
- **The Day screen**: "Reviewed and accepted" and the day lock are no longer two gestures. The review bar shows the state of the day and opens a three-valued control (To review, Reviewed, Frozen) with the review comment. "Frozen" asks for confirmation, saying that the solver will no longer touch the day; freezing without writing a comment keeps the review's comment. A read-only user sees the state, with no button. The progress figure and the banners count the days reviewed or frozen.
- **What you do**: if an assistant or a prompt names the MCP tools `lister_validations_journee`, `ajouter_validation_journee` or `retirer_validation_journee`, change the names, with no alias: `consulter_etats_journee` lists the state of each day and the progress, `modifier_etat_journee` (arguments `jour`, `etat`, `commentaire`) replaces the other two (`RELUE` or `FIGEE` to add, `A_RELIRE` to withdraw; only `FIGEE` lays the lock, and withdrawing a review no longer leaves a lock in place). Until 5.0, the routes `GET`, `POST /api/validations` and `DELETE /api/validations/{id}` remain aliases: they write the same reading and the same lock, and never remove a lock. A script that calls them must move to `/api/etats-journee` before 5.0.

### The forced assignment and the forced unavailability are converted

- **Before (3.x)**: an ad hoc exception had five types, among them the **forced unavailability** (a person ruled out of a timeslot, a stand or the whole event) and the **forced assignment** (at least one seat of the scope held by one of the named people).
- **After (4.0)**: three types ([ADR 0117](repo:docs/decisions/0117-deux-types-d-exception-les-forcees-sont-converties.md)): incompatibility, affinity, grouped arrival. The two rules `indisponibiliteForcee` and `affectationForcee` are removed (the number of rules goes from 42 to 40); their names are read with a warning in a 3.x file or copy. Migration `V161` converts each exception into what replaces it, without touching the saved plan:

| 3.x exception | Becomes |
| --- | --- |
| forced assignment on a timeslot | one lock staff member + timeslot for each named person who holds a seat of the scope on the saved plan |
| forced unavailability on a timeslot | the **whole day** added to the unavailable days of the fiche |
| forced unavailability with no timeslot | every day carrying a timeslot, added to the unavailable days of the fiche |
| forced unavailability on a stand; forced assignment with no timeslot, or that nobody holds | nothing: reported in the migration log, kept in the `contrainte_ad_hoc_avant_4_0` archive |

- **What is lost**: a forced unavailability on **a single timeslot** becomes a **whole day**: the fiche knows no timeslot. If the saved plan seats the person on another timeslot that day, it carries, after the migration, a hard availability breach: it shows on the Problems page, and the next solve moves the person. Each case is reported in the migration log (`RAISE WARNING`, one message per exception); read it before launching the first solve. The event-day mode also marks an absence by adding the **whole day** to the unavailable days of the fiche, whatever timeslot it started from.
- **What you do**: nothing for your data. The `contrainte_ad_hoc_avant_4_0` archive (`convertie` column: true or false) is neither read nor exported by the application and 5.0 drops it; once 4.0 is in place and a return to 3.x is ruled out, `DROP TABLE` removes it with no effect on the application. A script, prompt or MCP tool that created an `INDISPONIBILITE_FORCEE` or `AFFECTATION_FORCEE` exception is now refused: lock the person's timeslot (`verrouiller`, type `ANIMATEUR_CRENEAU`), or add the day to their `joursIndisponibles` (`modifier_animateur`). A 3.x YAML file carrying one of these types is read with the same conversion, a forced assignment being converted only if the file carries a plan (`plan:` section) where the person holds the seat; each case is a warning of the import report. The built-in help gives the gesture: "How to do without a forced assignment".

### The Day, Rail and Table views become the Day view

- **Before (3.x)**: for one day, the Planning page offered five renderings side by side, including "Table" (`?vue=calendrier`, open by default) and "Rail" (`?vue=rail`).
- **After (4.0)**: the table and the rail are two **modes** of a single **Day** view: `?vue=jour&mode=rail` or `?vue=jour&mode=tableau`. **The rail is the default mode**: an address with neither `vue` nor `mode` opens the rail, where it used to open the table. The review bar with the state of the day (to review, reviewed, frozen) stays in both modes.
- **What you do**: nothing for your links. `?vue=calendrier` and `?vue=rail` are read as before (the first opens the table) for the whole 4.x, and `/day-calendar` and `/rail-jour` lead to the right mode; 5.0 will remove the old values. A bookmark or an internal help page that should open the table must carry `mode=tableau`.

### The need reads in a single tab of the Diagnostic

- **Before (3.x)**: the staffing need, the volumetry of the problem (in the Solver) and the schedule read by game category (in the Planning, "By typologie", or `/typologies-planning`) were three readings on three screens.
- **After (4.0)**: the **Staffing need** tab of the Diagnostic gathers them: the exact bound and the margin per day, the need game category by game category, the "The schedule, typologie by typologie" section, the volumetry of the problem (at the bottom, no longer in the Solver) and "To train". Feasibility stays in the Problems tab, where its causes are.
- **What you do**: nothing for your links. `/typologies-planning` opens the `?onglet=besoin&section=typologie` section; `section=volumetrie` leads to the volumetry.

### The Planning page offers only four views

- **Before (3.x)**: the Planning page mixed two address keys. `?axe=jour|stand|personne|typologie` chose the axis, and `?vue=` the rendering of that axis (`calendrier`, `rail`, `carte`, `pauses`, `changements` for the day; `treemap`, `frise`, `synthese` for the grids). It also offered "Compare with...", which laid a second day beside the first.
- **After (4.0)**: four views, one key, `?vue=jour|stand|personne|carte`. "Day" keeps its two modes (`mode=rail|tableau`). "Stand" and "Person" are the two grids of the event; their own rendering (`treemap` for the hours breakdown, `frise` and `synthese` for people) moves to `?rendu=`. **Four readings leave the page**: "Compare two days" is removed; "By game category" is the *Typology* section of the *Staffing need* tab of the Diagnostic; the breaks without relay are read in *Diagnostic*, *Problems* tab; what moved since the last publication is read in *Publish*, *Send* tab, and what the last solve rewrote in the result of the *Solver*. The screen planned for the breaks ("Meals and breaks") will come in 4.x; until then, the old address leads to the screen that holds it today.
- **What you do**: nothing for your links. Until 5.0, `?axe=stand|personne` and the grid's `vue` (`treemap`, `frise`, `synthese`) are read as before and rewritten to the 4.0 form; `?axe=typologie` leads to the *Typology* section of the Diagnostic's *Staffing need*, `?vue=pauses` to *Problems*, `?vue=changements` to *Publish* (the day of `date` kept), and `/pauses`, `/intendance` and `/typologies-planning` to the same places. `?comparer=` and its keys (`ecarts`) are ignored. A bookmark or an internal help page that named one of these views should be moved to its new screen before 5.0, which will remove the old keys.

### The consigne is written as dated plages

- **Before (3.x)**: an edition consigne (a band closed for every stand, the compensation openings chosen stand by stand) was laid on top of the stands' hours at every read, writing nothing on them.
- **After (4.0)**: laying a consigne down **writes dated plages** on every stand of its date, marked as its own: a closure over the band, one over each timeslot it added, an opening per compensation window ([decision 0125](repo:docs/decisions/0125-la-consigne-s-ecrit-en-plages-datees.md)). These plages are read above the stand's own, and the resulting day is the same. Lifting the consigne removes exactly its plages; a consigne plage edited by hand in the meantime loses its mark and stays. The gestures (propose, preview, lay down, change, lift), the Consignes screen and the MCP tools `appliquer_consigne`, `lever_consigne`, `simuler_consigne` and `simuler_levee_consigne` do not change. Migration `V168` writes the plages of the consignes already laid, past ones included; one test compares, on every shipped scenario put under two consignes, the windows and seats obtained with those of 3.x, and another replays the migration against the application's writer.
- **What you do**: nothing for your data. A stand form opened before a consigne is laid or lifted is refused on save (reload it). A consigne's plages now appear among the stand's plages (`consigne: true` in the API); a script reading a stand's hours must read them along. A YAML export does not carry them: it carries the consigne, and the import writes them again.

### The two meal rules have only one line

- **Before (3.x)**: *Planning rules* showed two lines for the meal break, `coupureRepasObligatoire` (hard by default) and `coupureRepasPlacementPrefere` (a preference), and the direction of the preference was wired in: late at midday, early in the evening.
- **After (4.0)**: a single line for the meal break, with a choosable level (mandatory by default), with its link to the `placementRepas` setting of *Settings › Organisation* ([ADR 0123](repo:docs/decisions/0123-une-seule-entree-de-repas-placement-en-parametre.md)): `FIN_MIDI_DEBUT_SOIR` (default, the former direction), `DEBUT`, `FIN` or `AUCUN`. The two rules do **not** merge in the score: merged at a single level, they made four of the six shipped scenarios infeasible. `coupureRepasPlacementPrefere` stays a soft term of weight 1 under the line, and `GET /api/constraints` flags it `termeDe: coupureRepasObligatoire`. The MCP tool `modifier_parametres` (section `organisation`) and the YAML export (`parametresQualite.placementRepas`) carry the new setting.
- **What you do**: nothing for your plans: migration `V165` gives every edition the former direction, and no score moves; an edition that had disabled `coupureRepasPlacementPrefere` sees its placement become `AUCUN` (if it has stored its organisation settings; otherwise the toggle stays, and `PUT /api/constraints/coupureRepasPlacementPrefere` (`{"actif": true}`) restores it). A script that writes the whole organisation settings record without the `placementRepas` field puts it back to its default value. A script that read the list of rules and expected the `coupureRepasPlacementPrefere` line must skip the entries that carry `termeDe`, or read the setting. A weight, a toggle or a YAML file that still names this rule works as before.

### One timeslot generator

- **Before (3.x)**: four paths produced the grid in bulk, each with its routes and tools: the **day templates** and their calendar (`/api/journees-types`, nine `*_journee_type` and `*_journees_types` tools), the **recurring series** (`POST /api/creneaux/recurrence`, `creer_creneaux_recurrents`, `previsualiser_creneaux_recurrents`) and the **derivation from the stands' hours** (`POST /api/creneaux/derivation`, `previsualiser_derivation_creneaux`, `generer_creneaux_depuis_stands`).
- **After (4.0)**: one **timeslot generator** ([ADR 0126](repo:docs/decisions/0126-un-generateur-de-creneaux-unique.md)), with three gestures: a **preview** that writes nothing and checks the resulting grid, an **application**, and a **withdrawal** of dates from the calendar. It starts from one of three sources: the stands' hours (their model and their plages), the **templates** (« gabarits ») and a recurring pattern. The day templates become the generator's templates, with their name, shifts and dates: migration `V169` renames their tables (`gabarit`, `gabarit_vacation`, `gabarit_date`) without touching a row. A timeslot typed by hand does not change. The API is `/api/generateur-creneaux` (`GET` for the state, `POST /apercu` and `/application` with a `source`, `POST /retrait`, the templates under `/gabarits`, the calendar under `PUT /calendrier`); five MCP tools replace the twelve: `lister_gabarits`, `modifier_gabarit`, `supprimer_gabarit`, `previsualiser_generateur_creneaux` and `appliquer_generateur_creneaux`. The YAML moves to version 6: the `journeesTypes` section is called `gabarits`, entry for entry. A timeslot the generator creates on a day the edition did not count unfolds the stands' model, like one typed by hand. **The grid produced does not change**: a test replays each generation on every shipped scenario and compares the timeslots with those of 3.x.
- **What you do**: nothing for your data or your files. A template the generator could not apply (no shift, a zero-length shift or the same shift twice) is not converted: the migration stores it, with its dates, in the `journee_type_avant_4_0` table, readable until 5.0, and its dates are no longer governed (their timeslots stay). The screen does not change yet: it goes through the old routes, which remain aliases (`deprecated` in the OpenAPI) until 5.0, with their old keys (`journeesTypes`, `journeeTypeId`), like the twelve old MCP tools. A script or prompt that names them must move to the new names before 5.0 (see [the old tool names](../comprendre/mcp-outils.md#anciens-noms-doutils)).
